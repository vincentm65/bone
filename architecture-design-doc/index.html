Bone 2.4.5 · Architecture design guide

One brain.
Many ways in.

Bone is a coding assistant whose core runtime makes the decisions. The terminal, browser, remote client, and headless command are different windows onto that same runtime.

The shortest useful summary: keep intelligence and shared state in core, shared messages in protocol, and display concerns in the frontends.
01 · Mental model

Think of Bone as a small server with several remote controls.

The server is the daemon inside core. It owns conversations, asks language models for answers, runs tools, requests approvals, loads extensions, and saves durable data. A frontend sends commands and renders the events it receives.

One authority

There is one implementation of the agent loop: the core Driver. Frontends must not create their own version.

Explicit border

Anything crossing between daemon and client is represented by a type in protocol.

Replaceable edges

Providers, tools, Lua behavior, and UIs can vary while the central runtime rules stay consistent.

02 · Main parts

Each part has one clear job.

PartOwnsMust not own

Dependency direction: frontends depend on the contracts and capabilities below them. Core should never need to know how a terminal cell or browser element is drawn.
03 · One user turn

A message becomes a controlled loop.

A “turn” begins when a client submits a prompt and ends when the runtime produces a final outcome. One turn may call the model several times because tool results are fed back to it.

1

Command arrives

The client sends a RuntimeCommand over an in-process or newline-JSON connection.

2

Conversation actor routes it

The daemon finds the correct conversation. Work, approvals, and cancellation stay scoped to this conversation.

3

Session builds a Driver

RuntimeSession supplies transcript, tools, token totals, database identity, and cancellation state for this turn.

4

Hooks shape the request

Lua before_turn hooks may append instructions, replace effective history, or limit tools without becoming the runtime authority.

5

Model and tools loop

The Driver streams a provider response. Tool calls go through the registry and approval gate, then their results can trigger another provider request.

6

Outcome is folded back

The session updates durable messages and usage. All attached clients receive authoritative events needed to render the result.

Why separate Session and Driver?

RuntimeSession is the long-lived truth for a conversation. A Driver is assembled for one turn and owns active execution. This makes turn logic reusable in TUI, daemon, and headless modes without giving any frontend ownership of the conversation.

Concurrency rule: pair tool and shell events by protocol ID, not by arrival order. Different conversations and tool calls may run at the same time.
04 · State & configuration

Know which kind of truth you are changing.

Durable conversation state

SQLite is the source of truth for conversations, messages, usage, and runtime records. Complete display history remains available even if the model-facing history is compacted.

core-ownedsavedconversation-scoped

Live execution state

Active Driver data, pending events, status text, cancellation flags, and live view components are temporary. Do not treat them as persisted settings.

in memoryephemeral

Canonical configuration

YAML stores selected values. The daemon's ConfigStore validates all domains and publishes one revisioned snapshot to clients.

daemon-ownedrevisioned

Web-only metadata

The bridge may save browser-specific title and archive fields in webui_conversations. It must not rewrite core transcript data.

bridge-ownednarrow scope

Configuration domains

config.yamlGeneral behavior, approval, UI, themes, keymaps, and tool enablement.
providers.yamlProviders, models, endpoints, and credentials.
subagents.yamlNamed delegated-agent definitions and prompts.
extensions.yamlValidated values under each extension's namespace.
command-policy.yamlShell safety classifications.
init.luaStartup wiring and extension loading, not a second settings database.

Default config resolution: BONE_DIR, then $XDG_CONFIG_HOME/bone-rust, then ~/.bone-rust. Prefer daemon mutation APIs or /config; direct YAML edits are read at startup.

05 · Extensions

Rust supplies the platform. Lua supplies customizable behavior.

Bone embeds Lua 5.4. Lua can register tools, slash commands, hooks, themes, settings, keymaps, plugins, and declarative UI. If Lua startup fails, core warns and keeps running.

Rust guarantees                    Lua chooses
────────────────────────────────   ────────────────────────────────
tool registry + approval gate      custom tool behavior
protocol + view primitives         panes, commands, status content
validated config storage           extension schemas and values
provider request primitive         compaction policy and prompts
session + cancellation ownership   request-shaping hooks
No bypassLua file writes and shell calls still pass through native approval and command policy.
Protected coreNative tools and core slash commands cannot be overridden.
Declarative UILua emits ViewDiff updates; each frontend decides how to render them.
Thin initKeep init.lua as wiring. Put implementations in purpose-specific files under lua/.
Policy in LuaCompaction is deliberately implemented as catalog Lua. Core only applies a validated conversation.replace action.
06 · Delegated agents

Subagents are bounded workers, not new authorities.

The main agent owns the user-facing turn at depth 0. A delegated agent receives a self-contained task, separate prompt/transcript, tool allow-list, approval mode, timeout, and optional provider override.

Isolation

A child returns a result to its caller. It does not own or directly become the parent conversation.

Limits

Subagents cannot create nested subagents. Output, inactivity, wall time, tools, and provider concurrency can be bounded.

Ownership

The daemon owns job records, cancellation, approval behavior, and result delivery. Job IDs are conversation-scoped.

Foreground versus background

run waits for a result. spawn starts a background job. The interactive TUI can inject an unconsumed completed result when idle; headless callers wait because there is no idle UI loop. Cancellation is cooperative and explicit job cancellation is different from cancelling a wait.

07 · Frontends

Different screens, one contract.

ModeConnectionSpecial concern
Local TUIClient beside an in-process daemon.Terminal layout, input, live approvals, panes.
bone serveNewline-JSON over a socket.No authentication; bind to loopback unless the network is trusted.
Remote TUIbone --connect to a daemon.Reconnect from daemon snapshots, not guessed local state.
WebBrowser HTTP/SSE → Node bridge → runtime protocol.Sanitize model Markdown; keep web metadata separate.
Headlessbone run uses core directly.No interactive approval pane or live terminal view.

A client should behave like a reducer: send a command, then update its local visual state from RuntimeEvent and snapshots. A click is only a request. The daemon's response confirms whether the mutation happened.

Browser safety: model text is hostile input. Raw HTML is shown as text and rendered Markdown is sanitized before DOM insertion.
08 · Decision guide

Where should a new change live?

Does it change agent behavior, approvals, tools, shared state, or persistence?Put the authority in core. If a client must trigger or observe it, add protocol types too.
Does data cross the daemon/frontend boundary?Define it in protocol first. Update every client and contract test.
Is it only terminal layout, wrapping, cursor, or key handling?Put it in tui. Do not teach core about terminal cells.
Is it only browser presentation or browser metadata?Put it in webui. Keep shared behavior out of the bridge.
Is it optional policy or user customization?Prefer a purpose-specific Lua extension using the existing APIs. Store values in namespaced canonical config.
Must it survive restart?Choose the right durable owner: core SQLite for conversation/runtime data, YAML for configuration, or the narrow web metadata table.

Feature recipe

  1. Write down who owns the truth and its lifetime.
  2. Add or update the shared protocol contract if the boundary changes.
  3. Implement daemon routing and core behavior.
  4. Make frontends render the same resulting event or snapshot.
  5. Test approval, cancellation, reconnect, and multiple clients where relevant.
  6. Exercise at least one real frontend workflow, not only unit tests.
09 · Risks & tradeoffs

The architecture protects consistency, but asks for discipline.

Frontend drift

Risk: TUI and web behave differently. Defense: put semantics in core and share protocol events; keep only presentation local.

Split-brain state

Risk: a client assumes a mutation succeeded. Defense: wait for the daemon's event or revisioned snapshot.

Extension power

Risk: flexible Lua can become a parallel platform. Defense: preserve native approvals, schemas, protected names, and bounded APIs.

Concurrent event order

Risk: interleaved output is attached to the wrong work. Defense: use conversation, turn, call, and job IDs.

Remote exposure

Risk: bone serve has no authentication. Defense: default to loopback and use only trusted transport when remote.

Durability confusion

Risk: ephemeral view or Driver state is treated as saved. Defense: make persistence explicit through core session/config paths.

Core vocabulary

DaemonThe process-level authority that owns sessions, configuration, jobs, and client connections.
RuntimeSessionThe long-lived truth for one conversation across turns.
DriverThe execution engine for one turn: provider/tool loop, approvals, events, and cancellation.
ProtocolThe shared language spoken across frontend and daemon boundaries.
ViewDiffA declarative UI update that any frontend can render in its own way.
Conversation actorThe daemon-side unit that serializes and scopes work for one conversation.

This document summarizes the architecture currently described by Bone's generated core references and source layout. When behavior changes, the canonical topic documents under core/defaults/docs/ should change with it.
